# T3 Application mapping

## Native authority

T3 owns native Projects, Threads, messages, activities, requests, execution,
model/provider/runtime controls, history, and retention.

T3 uses independent HTTP request/response operations rather than a persistent
App Server session. Its optional diagnostic provider therefore returns the
configured Application identity with `connection=None`; it does not fabricate
an epoch, reconnect counter, or dispatch queue to imitate Codex.

The adapter and authenticated HTTP client are co-located in
`src/imagent/applications/adapters/t3.py`. `imagent.applications` lazily
re-exports the exact `T3ApplicationAdapter`, `HttpT3Client`, and
`T3ClientError` objects from that module; the historical `t3.py` and
`t3_client.py` paths are not retained.

## Mapping

- SDK Project and Thread map to real T3 resources.
- every native Thread without a stable native Project ID is rejected as an
  invalid resource rather than projected into a Project-less branch;
- every supplied `ThreadRef` is matched against authoritative native
  `(projectId, id)` before projection, input, polling, delete, or interrupt;
- native messages and activities are grouped by `turnId` for history/catch-up.
- external client-user IDs round-trip into the same canonical projection as
  local T3 input.
- polling/native state changes become stable Agent events.
- all meaningful completed Agent messages are preserved before a terminal Turn
  status.
- per-Thread input dispatch and authoritative detail lookup are serialized
  because T3's accepted Turn identity is read from `latestTurn`; concurrent
  callers must not both observe the later Turn.
- input uses stable native `commandId` and `messageId` values derived from the
  SDK client message ID. T3 command receipts therefore provide the native
  deduplication guarantee for an ambiguous dispatch; the adapter does not
  invent a second local retry identity.
- the adapter accepts the SDK's default continuation preference but returns
  `started/create_new`; the evidenced T3 command surface has no native
  active-Turn continuation mutation.

T3 discovery and reads remain native. The current evidenced T3 protocol does
not expose CWD Project creation, so `project.create` is advertised and returned
as typed unsupported; the adapter never guesses an endpoint.

## Recovery guarantees

The adapter declares only ordering and replay behavior supported by its native
client. Without a restart-safe cursor/sequence, it uses authoritative detail
reads and stable IDs rather than synthetic counters.
`event_buffer_max_pending` bounds each polling subscriber; overflowing one
subscription removes it without retaining polling output as a hidden journal
or stopping unrelated subscribers.

The adapter also bounds its process-local identity state with explicit
constructor capacities: 4096 `(Thread, Turn)` baselines, 1024 active Thread
send locks, 8192 `(Thread, message)` dedupe identities, and 4096 `(Thread,
Turn)` terminal identities by default. Baseline admission happens before the
pre-dispatch callback and native start. An active baseline is never evicted;
only the oldest baseline already marked terminal may leave the table. If no
terminal entry can be evicted, the input is rejected before native mutation.
Send locks count owners and waiters, are removed at zero users, and reject a
new Thread when their active-key bound is full. Seen-message and terminal-Turn
identities use deterministic oldest-first windows. An evicted dedupe identity
may be replayed by native history, but native authority is not dropped and no
SDK transcript, spool, or outbox is created.

The optional concrete `T3ActivityPresenter` receives only bounded frozen
`T3ActivityFacts`, not the native Thread detail or HTTP client. Its output is
bounded text; the adapter fixes stable activity/Thread/Turn identity,
assistant role, creation time, and namespaced `kind`/`source=activity`
metadata. The same normalization and presenter invocation is used by live
polling, catch-up, and history, so configured output is recoverable and may be
`message.completed`. Activity IDs have a deduplication domain separate from
message IDs. Implementations must be replay-safe and cannot use invocation as
a one-time external side effect.

Live normalization uses one finite per-Thread state table and merges message
and activity candidates in the same native-time order as catch-up/history.
Once native acceptance and Turn identity are known, the adapter returns the
successful `AcceptedTurn` immediately, before any observation or configured A1
work; `send_input` never synchronously publishes the just-accepted Thread
state. The existing sole poll/history path performs observation and
presentation and cannot prevent Core from recording reply correlation. A
polling failure terminates that Thread subscription with an explicit
recoverable gap instead of leaving a silent stalled observer.
The finite live identity window retains a stable native activity cursor. If
that cursor disappears or more new activities arrive than the configured
window can admit, the adapter emits an explicit poll-window recovery gap; it
never truncates unseen recoverable activities and continues checkpointing.
An active poll pins its finite Thread state so LRU eviction cannot silently
discard the cursor; exhausted pinned capacity also fails explicitly. Partial-
attempt deduplication retains only the current bounded candidate batch.

T3 input follows the native outcome boundary: validation, baseline read,
command construction, and capacity reservation finish before the typed
pre-dispatch callback. Callback failure performs zero native dispatch. After
the one dispatch attempt, any ordinary exception or cancellation from
dispatch or the authoritative follow-up Thread read, including a missing
Turn ID, becomes `ApplicationInputOutcomeUnknown` with its original cause.
An already-typed unknown is preserved, no second dispatch/fallback is allowed,
and only the local baseline reservation is released.

Without a presenter, current T3 polling and authoritative history/catch-up
mapping are unchanged; no new live activity event is emitted. Presentation
does not add another poller or subscriber.

T3 activities name approval/user-input request and resolution events, but the
current native client contract contains no evidenced response endpoint or
pending-request snapshot. The adapter therefore advertises interactive
requests as unsupported and does not infer a dispatch command.

## Attachments and product policy

Native image/data encoding is T3 adapter behavior and follows declared source
capabilities plus the shared trust boundary. T3 acquires rooted image bytes
through the no-follow descriptor chain and embeds those exact bounded,
size/digest-checked bytes in the native data URL. T3 Full Access,
provider/model, workspace, and runtime-mode choices are consumer/adapter
configuration, not SDK permission policy.
