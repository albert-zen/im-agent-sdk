# T3 Application mapping

## Native authority

T3 owns native Projects, Threads, messages, activities, requests, execution,
model/provider/runtime controls, history, and retention.

## Mapping

- SDK Project and Thread map to real T3 resources.
- native messages and activities are grouped by `turnId` for history/catch-up.
- external client-user IDs round-trip into the same canonical projection as
  local T3 input.
- polling/native state changes become stable Agent events.
- all meaningful completed Agent messages are preserved before a terminal Turn
  status.
- per-Thread input dispatch and authoritative detail lookup are serialized
  because T3's accepted Turn identity is read from `latestTurn`; concurrent
  callers must not both observe the later Turn.
- input uses stable native `commandId` and `messageId` values derived from the
  SDK client message ID. T3 command receipts therefore provide the native
  deduplication guarantee for an ambiguous dispatch; the adapter does not
  invent a second local retry identity.
- the adapter accepts the SDK's default continuation preference but returns
  `started/create_new`; the evidenced T3 command surface has no native
  active-Turn continuation mutation.

## Recovery guarantees

The adapter declares only ordering and replay behavior supported by its native
client. Without a restart-safe cursor/sequence, it uses authoritative detail
reads and stable IDs rather than synthetic counters.

T3 activities name approval/user-input request and resolution events, but the
current native client contract contains no evidenced response endpoint or
pending-request snapshot. The adapter therefore advertises interactive
requests as unsupported and does not infer a dispatch command.

## Attachments and product policy

Native image/data encoding is T3 adapter behavior and follows declared source
capabilities plus the shared trust boundary. T3 Full Access, provider/model,
workspace, and runtime-mode choices are consumer/adapter configuration, not
SDK permission policy.
