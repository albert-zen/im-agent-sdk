# V1 capability ownership matrix

This matrix is an implementation-facing companion to the normative
[v1 design](../V1_DESIGN.md) and
[executable specification](../V1_EXECUTABLE_SPEC.md). It records who owns a
capability and what the current SDK actually supports; it does not create a new
capability or override an ADR or component design.

The implementation and tests were audited at repository base `a72b24a` on
2026-08-13. The categories below apply the admission rule in
[ADR 0006](../decisions/0006-core-admission-and-policy-ownership.md): common
Agent semantics need evidence from two Agent Applications, common Channel
semantics need evidence from two Channels, and one-product behavior stays in a
concrete adapter or consumer. A row's category is its primary ownership
classification; the owner column calls out adjacent responsibilities that must
not move with it.

## Audit risks and non-promotions

- No authoritative doc/code contradiction was found in the audited scope.
- Native cursor replay is a deliberate optional contract and is exercised by a
  replay-capable test adapter, but no current first-party Codex, Zen, or T3
  adapter advertises it. The matrix therefore does not describe native replay
  as current first-party support; current restart acceptance uses authoritative
  history/catch-up.
- App Server's concrete Thread-option seam is evidence for adapter-specific
  profiles, not evidence for a common profile vocabulary. Likewise, its shared
  transport does not make Codex-only request or presentation behavior a Zen
  capability.
- The common media contract standardizes source and trust semantics, not path
  access. T3's rooted byte acquisition, App Server's path-only rejection, and
  the consumer-owned artifact ledger are intentionally different outcomes.
- Permissions, credentials, commands, model choice, retry/capacity policy, and
  presentation remain downstream even where the SDK provides a typed action,
  registry, authorizer reference implementation, or presentation seam.
